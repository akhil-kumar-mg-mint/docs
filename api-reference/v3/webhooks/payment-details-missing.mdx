<Warning>
  **This event is being retired. Move to [`VERIFICATION_NEEDED`](/api-reference/v3/webhooks/verification-needed).**

  Which of the two events you received for a payment that could not be filed
  depended on which rail the money arrived through, not on what was actually
  wrong — a distinction no integration should have had to model.
  `VERIFICATION_NEEDED` is becoming the single signal for all of it.

  **The move has already started.** Virtual Bank Account credits on the ICICI
  rail raise `VERIFICATION_NEEDED` today, carrying the same list this event
  used to carry behind it. The remaining rails still raise this event; they
  follow.

  If you handle this event today, handle `VERIFICATION_NEEDED` too — the
  mapping is below, and a handler that reads both is correct throughout the
  transition.

  The event type itself is not removed — historical deliveries and your stored
  records keep reading correctly. You simply stop receiving new ones.
</Warning>

## What replaces it

`VERIFICATION_NEEDED` carries the same information, in the body every
verification event now shares:

| This event | `VERIFICATION_NEEDED` |
|---|---|
| `data.payment_id` | `data.payment_id` (unchanged) |
| `data.order_uid` | `data.order_id` |
| `data.details_missing` | `data.action_required_fields` — the same field names |
| `data.message` | `data.message` (different wording, still not a value to branch on) |
| — | `data.verification_status`, so one handler can tell an ask from an `IN_REVIEW` or an `EXPIRED` |
| — | `data.payment_verification_expiry`, the deadline where one applies |

Nothing is lost in the move, and one key is gained that matters: this event
only ever means "something is missing", so a partner had no way to learn from
it that a payment had *stopped* needing anything. `verification_status` says
that, and the same body with an empty list arrives as
[`PAYMENT_UNDER_REVIEW`](/api-reference/v3/webhooks/payment-under-review) when
the payment is accepted.

<Note>
  **LRS payments are unaffected either way.** They receive
  [`LRS_VERIFICATION_NEEDED`](/api-reference/v3/webhooks/lrs-verification-needed)
  today and will continue to — it names documents as well as fields, which neither
  of the generic events does.
</Note>

## Event Overview

**Event Type**: `PAYMENT_DETAILS_MISSING`  
**Category**: Payment  
**Description**: Payment was recorded but one or more order fields required for payment verification are missing.

This webhook names the fields missing for payment verification, so you can supply them via the Partner API or the dashboard.

It covers Virtual Bank Account credits and regular payment-success flows — **except credits on the ICICI rail, which already raise [`VERIFICATION_NEEDED`](/api-reference/v3/webhooks/verification-needed) instead**. That is the first step of the retirement above; a payment never gets both.

<Note>
  **Not sent for LRS payments.** A payment settling under an LRS purpose code receives [`LRS_VERIFICATION_NEEDED`](/api-reference/v3/webhooks/lrs-verification-needed) instead, which names the documents it needs as well as the fields. It never receives both.

  A payment whose purpose code is not yet known still receives this event; the LRS one follows once the code is declared.
</Note>

### When the webhook is sent

The webhook is sent **only when all** of the following are true:

1. **Merchant has webhook URL** – Your merchant account (or parent, for sub-merchants) has an active API credential with a non-empty webhook URL.
2. **At least one detail is missing** – The payment still owes at least one verification field (see [details_missing](#details_missing-field-names) below). When nothing is outstanding, no webhook is sent — silence is the “nothing owed” signal.

## Classification

This event fires **instead of** [`LRS_VERIFICATION_NEEDED`](/api-reference/v3/webhooks/lrs-verification-needed), and one common reason is that the payment could not be classified. Two facts decide that — the buyer type and the FEMA purpose code — and either one we could not resolve appears in `details_missing` alongside the order fields:

```json
{
  "details_missing": ["buyer_name", "purpose_code"]
}
```

| Field | Meaning |
|-------|---------|
| `purpose_code` | No FEMA purpose code has been declared for this order. |
| `business_model` | Nothing has *declared* whether the buyer is `B2C` or `B2B`. |

`business_model` is listed when nothing has declared it — not when it is empty.
It is never empty; it defaults to `B2C`. A default nobody stood behind is worth
telling you about.

They are ordinary entries in that list, not a section of their own: they are
details that are missing, so they belong in the one list you already read. What
we *did* resolve is not reported — you declared it.

<Note>
  Both are named the same way on `VERIFICATION_NEEDED` — as plain entries in
  `action_required_fields` — so the move costs you no translation. See
  [What replaces it](#what-replaces-it).
</Note>

<Tip>
  **Supplying these switches the payment over.** Without a purpose code there is no
  requirement set, so we cannot say what the payment owes beyond the generic fields.
  Declare it — through [Submit Verification Details](/api-reference/v3/lrs/submit-verification-details) — and
  [`LRS_VERIFICATION_NEEDED`](/api-reference/v3/webhooks/lrs-verification-needed)
  takes over with the full, purpose-code-specific list.
</Tip>

## Delivery Details

| Attribute | Value |
|-----------|--------|
| **HTTP method** | `POST` |
| **URL** | The webhook URL configured on your merchant account's API credentials |
| **Content-Type** | `application/json` |
| **Timeout** | 10 seconds |
| **Retries** | Up to 5 delivery attempts (backoff: 1 min, 5 min, 15 min, 60 min) |

### Headers

| Header | Description |
|--------|-------------|
| `Content-Type` | `application/json` |
| `User-Agent` | `Eximpe-Webhook/1.0` |
| `X-Webhook-Event` | `PAYMENT_DETAILS_MISSING` |
| `X-Webhook-Timestamp` | Unix timestamp (string) at the time of the request |
| `X-Webhook-Signature` | `HMAC-SHA256(encryption_key, raw_body)`, hex-encoded |
| `X-Webhook-Signature-V2` | `t=<timestamp>,v2=<hex>` where the digest is `HMAC-SHA256(encryption_key, "<timestamp>." + raw_body)` |

**Verifying.** The body is serialised once and those exact bytes are both sent and signed, so hashing the raw request body as received is correct — do not re-serialise the parsed JSON first.

Prefer **V2**: the timestamp is inside the signed material, so a captured delivery cannot be replayed with a fresh one. V1 stays alongside it so nobody has to migrate on our schedule.

### details_missing field names

What the list holds depends on whether the payment has been classified.

**Before classification** — the two classifying facts, plus the plain order-field check:

| Field name | Description |
|------------|-------------|
| `business_model` | Buyer type — nothing has declared `B2C` or `B2B`. |
| `purpose_code` | FEMA/FETERS purpose code — none has been declared for this order. |
| `buyer_name` | Name of the buyer/importer. |
| `product_description` | Description of the product or goods. |
| `invoice_number` | Invoice number. |
| `buyer_postal_code` | Buyer's postal/ZIP code. |
| `hs_code` | HS code — only checked when the order ships physical goods. |

Supply these through [Upload Payment Verification Details](/api-reference/v3/payment/upload-verification-details), or the classifying pair through [Submit Verification Details](/api-reference/v3/lrs/submit-verification-details).

**After classification** — the outstanding codes of the payment's own checklist, which is a longer and more specific list: `buyer_address_line_1`, `buyer_city`, `buyer_state`, `buyer_email`, `buyer_phone`, `invoice_date`, `iec`, `buyer_pan`, `invoice`, and so on. These are answered through [Submit Verification Details](/api-reference/v3/lrs/submit-verification-details), under the same codes.

<Note>
  **Do not hardcode either list.** [Get Verification Requirements](/api-reference/v3/lrs/verification-requirements) returns the whole set for a payment, each item carrying its own `satisfied` flag. It is authoritative, idempotent, and revised as the underlying regulatory matrix is.
</Note>

## What to Do When You Receive This Webhook

1. **Respond with HTTP 2xx** (e.g. `200 OK`) as soon as you have accepted the payload, so the platform marks the delivery as successful and does not retry.
2. **Verify the signature** against the raw request body — prefer `X-Webhook-Signature-V2`.
3. **Use `order_uid` and `payment_id`** to fetch full order/payment details from the Partner API if needed (e.g. amount, status).
4. **Supply what `details_missing` names.** Order fields go to [Upload Payment Verification Details](/api-reference/v3/payment/upload-verification-details); the classifying pair and any checklist codes go to [Submit Verification Details](/api-reference/v3/lrs/submit-verification-details). If you are unsure which takes a given code, [`GET` the payment's verification requirements](/api-reference/v3/lrs/verification-requirements) — anything it lists is answered on that same path.
5. **Handle [`VERIFICATION_NEEDED`](/api-reference/v3/webhooks/verification-needed) as well.** It already carries this list for some rails, and will carry it for all of them.
