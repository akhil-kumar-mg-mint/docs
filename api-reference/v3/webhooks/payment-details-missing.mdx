## Event Overview

**Event Type**: `PAYMENT_DETAILS_MISSING`
**Category**: Payment Verification
**Description**: A successful payment still owes verification details before it can settle

This webhook names what a payment is missing once it has succeeded. Send the codes it lists back through [Submit Payment Verification Details](/api-reference/v3/payment/submit-verification-details).

<Note>
  **It always comes with a [`VERIFICATION_NEEDED`](/api-reference/v3/webhooks/verification-needed).** Each time this event is sent, a `VERIFICATION_NEEDED` with `verification_status: "ACTION_REQUIRED"` is sent alongside it. Its `action_required_fields` holds the same codes as `details_missing`. If you handle both, treat them as one ask for the same `payment_id`.
</Note>

<Note>
  **Not sent for LRS payments.** A payment settling under an LRS purpose code receives [`LRS_VERIFICATION_NEEDED`](/api-reference/v3/webhooks/lrs-verification-needed) instead. **Not sent for Virtual Bank Account credits either**: those are asked through `VERIFICATION_NEEDED` alone.
</Note>

### When the webhook is sent

1. **A payment succeeded** and its order is missing verification details.
2. **You declared a payment's `business_model` and `purpose_code`** through Submit Payment Verification Details, and the payment's checklist has a verification step that still needs items.
3. **A `buyer_pan` you sent was rejected.** The payment is asked again, and the list names `buyer_pan` with everything else still owed. See [Buyer PAN verification](/integration-guide/v3/web-integration/buyer-pan).

It is sent only when the list is not empty, and never once the payment has reached `UNDER_REVIEW` or a later settlement status.

The webhook is **delivered only if** your merchant account (or parent, for sub-merchants) has an active API credential with a non-empty webhook URL.

## Delivery Details

| Attribute | Value |
|-----------|--------|
| **HTTP method** | `POST` |
| **URL** | The webhook URL configured on your merchant account's API credentials |
| **Content-Type** | `application/json` |
| **Timeout** | 10 seconds |
| **Retries** | Up to 5 delivery attempts (backoff: 1 min, 5 min, 15 min, 60 min) |

### Headers

| Header | Description |
|--------|-------------|
| `Content-Type` | `application/json` |
| `User-Agent` | `Eximpe-Webhook/1.0` |
| `X-Webhook-Event` | `PAYMENT_DETAILS_MISSING` |
| `X-Webhook-Timestamp` | Unix timestamp (string) at the time of the request |
| `X-Webhook-Signature` | `HMAC-SHA256(encryption_key, raw_body)`, hex-encoded |
| `X-Webhook-Signature-V2` | `t=<timestamp>,v2=<hex>` where the digest is `HMAC-SHA256(encryption_key, "<timestamp>." + raw_body)` |

Verify against the raw request body as received, and prefer V2. See [`VERIFICATION_NEEDED`](/api-reference/v3/webhooks/verification-needed#headers) for why.

## Reading `details_missing`

**A classified payment** — one whose `business_model` and `purpose_code` are both declared — lists its checklist's outstanding codes, such as `buyer_city`, `iec`, `buyer_pan` or `invoice`. These are the same codes [Get Verification Requirements](/api-reference/v3/lrs/verification-requirements) reports as not `satisfied`.

**A payment nobody has classified yet** lists:

| Code | Meaning |
|---|---|
| `business_model` | Nothing has declared whether the buyer is `B2C` or `B2B`. |
| `purpose_code` | No FEMA/FETERS purpose code has been declared for the order. |
| `buyer_name` | The order has no buyer name. |
| `product_description` | The order has neither a product name nor a description. |
| `invoice_number` | The order has no invoice number. |
| `buyer_postal_code` | The order has no buyer postal code. |
| `hs_code` | The order ships physical goods and has no HS code. |
| `buyer_pan` | The payment is collected by EximPe and the order has no buyer PAN. A PAN already on the order is checked once you classify the payment. |

Send `business_model` and `purpose_code` first, or in the same call as the rest. Until both are declared nothing else can be checked. See [Submit Payment Verification Details](/api-reference/v3/payment/submit-verification-details#which-codes-to-send).

### `buyer_pan`

`buyer_pan` asks for the buyer's PAN, on payments that EximPe collects and that are not LRS. It is named only after the PAN on the order, if any, has been checked with the issuer; if the issuer's service is down, this event waits until the check can run. Until a verified PAN is on file, the payment stays in `ACTION_REQUIRED` and does not settle. See [Buyer PAN verification](/integration-guide/v3/web-integration/buyer-pan).

## What to Do When You Receive This Webhook

1. **Respond with HTTP 2xx** (e.g. `200 OK`) as soon as you have accepted the payload, so the delivery is not retried.
2. **Verify the signature** against the raw request body — prefer `X-Webhook-Signature-V2`.
3. **Use `payment_id` and `order_uid`** to reconcile with your system.
4. **Collect what `details_missing` names** and send it to [Submit Payment Verification Details](/api-reference/v3/payment/submit-verification-details) under the same codes. Its response lists what is still `outstanding`, so you do not need to wait for another event.
