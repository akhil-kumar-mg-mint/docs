## Overview

Changes the details of a sub-merchant that is still `PENDING` or `CHANGES_REQUESTED`. Send only the fields you want to change; everything you leave out keeps its stored value.

```bash
curl -X PATCH 'https://api-pacb-uat.eximpe.com/partners/merchants/6182929449/' \
  -H 'X-Client-ID: <client_id>' -H 'X-Client-Secret: <client_secret>' \
  -H 'X-API-Version: 3.0.0' \
  -H 'Content-Type: application/json' \
  -d '{ "global_company": { "registration_number": "U72200MH2020PTC654321" } }'
```

## When you can edit

| Status | Edit allowed? | What the edit does |
|---|---|---|
| `PENDING` | Yes | Saves the change. The application stays `PENDING`; EximPe is not notified again. |
| `CHANGES_REQUESTED` | Yes | Saves the change, then resubmits if the application is complete. See [Resubmitting](#resubmitting). |
| `IN_REVIEW`, `APPROVED`, `REJECTED` | No | Refused with a `409`. |

<Note>
  **Sandbox sub-merchants you create cannot be edited.** A sub-merchant created through the API in sandbox is approved immediately, so it is never `PENDING` or `CHANGES_REQUESTED` there: edits are refused with a `409`, and resubmitting cannot be tried. The API offers no way to change this. Contact EximPe if you need a sandbox sub-merchant in another status to test with.
</Note>

## The request

The fields and rules are the same as [Create Merchant](/api-reference/v3/merchant/create#the-request). On an edit every field is optional:

- **Top-level fields** (`legal_name`, `brand_name`, `email`, `phone_number`): send any of them on their own.
- **`global_company` and `settlement_details`:** send only the fields inside them that you want to change.
- **Changing `bank_swift_code`:** bank fields you leave out (`bank_name`, `bank_branch_name`, `bank_address`, `bank_city`, `bank_pincode`, `bank_country`) are filled from the new code, replacing the stored values. Values you send are kept as sent. If the code is unchanged or left out, nothing is filled. The same refusals apply as on [Create Merchant](/api-reference/v3/merchant/create#settlement): each field the lookup leaves empty is listed in `details.settlement_details`, and a filled value that fails its field rule is listed under its field.
- **`beneficial_owners`:** the list is replaced whole.
- **Communication address:** while `same_as_registered_address` is `true`, whether sent in this edit or already stored, the communication fields follow the registered address. When it is `false`, every communication field must have a value, sent in this edit or already stored.

### Beneficial owners

| You send | Result |
|---|---|
| No `beneficial_owners` key | The stored owners are kept. |
| A list of owners | The stored owners are replaced with exactly this list. Send every owner you want to keep, not only the new ones. |
| `[]` | The stored owners are removed; the sub-merchant has no owners. |

Each owner takes the same fields as on create, including the optional `identify_number` (registration number — company owners only, optional). The same limits apply as on create: owners are optional, each owner needs at least 10%, and the total is at most 100%. Owners are accepted only when your account collects under EximPe's own PA-CB licence. No API field returns which licence your account uses; see [Which licence applies to you](/api-reference/v3/merchant/create#beneficial-owners).

### Fields you cannot send

Send only the fields listed on [Create Merchant](/api-reference/v3/merchant/create#the-request). Any other field, at the top level or inside `global_company`, `settlement_details` or a beneficial owner, is refused with a `400`, and nothing is saved. Each refused field is listed in `details` where you sent it, e.g. `details.global_company.category` says `["category is not accepted"]`. Owner `id`s from a response are not accepted either; send each owner without its `id`.

`status`, `sub_merchant_status` and `is_active` are refused at the top level with a `400`, and nothing is saved; `details` lists each one, e.g. `details.status` says `["status cannot be set"]`. Status changes come from EximPe's review and from resubmitting. To remove a sub-merchant, use [Delete Merchant](/api-reference/v3/merchant/delete). Settlement currency always follows your own settlement account and cannot be edited; a `settlement_currency` you send is refused like any other unlisted field.

## Resubmitting

There is no separate resubmit call. When you edit a `CHANGES_REQUESTED` sub-merchant, EximPe checks the whole application as it stands after your edit:

- **Complete:** the status moves to `PENDING` and EximPe is notified once to review it again. The reasons EximPe gave are cleared from `changes_requested_reason` and `section_reasons`.
- **Not yet complete:** your edit is saved and the status stays `CHANGES_REQUESTED`. Send the missing fields in another edit; the one that completes the application resubmits it.

An application is complete when:

- Every field marked required on [Create Merchant](/api-reference/v3/merchant/create#the-request) has a value.
- At least one HS code is stored, if a goods category is selected.

Beneficial owners are optional and do not affect completeness.

<Note>
  **Some sections cannot be fixed through the API.** When `section_reasons` names `authorized_persons` or `security_assessment`, no field on this endpoint changes that part of the application. Contact EximPe to resolve it.
</Note>

<Tip>
  Read `changes_requested_reason` and `section_reasons` from [Get Merchant](/api-reference/v3/merchant/get) to see what to fix. Then send everything in one edit, so the sub-merchant goes back for review in one step.
</Tip>

## Errors

Errors use the standard envelope. For a `400`, `details` lists every problem in the edit, each field mapped to a list of messages; fields that are not accepted, status fields and bank fields the SWIFT lookup could not fill appear alongside the other field errors. Rules across fields, such as the HS code rule and the ownership total, are reported once the other fields in their section are valid. Otherwise `details` is an empty object. For the shapes and which code you get, see [Create Merchant](/api-reference/v3/merchant/create#errors).

| HTTP | Cause | `code` | What to do |
|---|---|---|---|
| `400` | A field fails a rule from [Create Merchant](/api-reference/v3/merchant/create#errors) | `ERR_MERCHANT_001` | `details` names each field with the reason. Nothing is saved; fix the fields and send the edit again. |
| `400` | A field not listed on [Create Merchant](/api-reference/v3/merchant/create#the-request) is sent, at the top level, in `global_company`, in `settlement_details` or in an owner | `ERR_MERCHANT_001` | `details` lists each field where you sent it, e.g. `"settlement_currency": ["settlement_currency is not accepted"]`. Nothing is saved; remove it. |
| `400` | `status`, `sub_merchant_status` or `is_active` sent | `ERR_MERCHANT_005` when it is the only problem, otherwise `ERR_MERCHANT_001` | Remove the field. |
| `400` | `bank_swift_code` changed, bank fields were left out and no bank details were found for the new code, or the bank details found have no value for some of them | `ERR_MERCHANT_019` when it is the only problem, otherwise `ERR_MERCHANT_001` | `details.settlement_details` lists the fields still missing. Send them, or check the code. |
| `400` | `bank_swift_code` changed, `bank_country` was left out and the bank's country is not one of the supported countries | `ERR_MERCHANT_006` when it is the only problem, otherwise `ERR_MERCHANT_001` | Send `bank_country`. |
| `401` | Missing or invalid credentials | `ERR_AUTH_000`, `ERR_AUTH_001` | Check `X-Client-ID` and `X-Client-Secret`. |
| `403` | Your account is not a PSP | `ERR_AUTH_003` | Only PSPs can manage sub-merchants. |
| `403` | Your account is a PSP, but not set up for import collections | `ERR_MERCHANT_017` | Contact EximPe. |
| `404` | No sub-merchant with this ID belongs to you, or it has been deleted | `ERR_MERCHANT_016` | Check the ID. |
| `409` | The sub-merchant is `IN_REVIEW`, `APPROVED` or `REJECTED` | `ERR_MERCHANT_003` | It can no longer be edited. |
