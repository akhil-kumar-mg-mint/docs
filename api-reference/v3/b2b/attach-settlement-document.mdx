---
title: 'Attach Settlement Document'
description: "Attach an already-uploaded file as one post-settlement compliance document, by its ref."
openapi: 'POST /pg/payments/{payment_id}/settlement-documents/'
---

## Overview

Attaches evidence that a settled B2B-services payment's service was delivered.

**This endpoint never takes a file.** You upload once through the ordinary document endpoint and attach the `ref` it hands back — the same upload-once, reference-by-id pattern the verification step uses. One upload can therefore be referenced more than once without the bytes ever being copied.

## The two calls

<Steps>
  <Step title="Upload the file">
    `POST /pg/payments/{payment_id}/documents/` as `multipart/form-data`, with `type=delivery_proof`. The response carries a `ref`.
  </Step>
  <Step title="Attach it">
    `POST` here with `{"doc_type": "delivery_proof", "ref": "<that ref>"}`.
  </Step>
</Steps>

```bash
# 1. upload
curl -X POST 'https://api-pacb-uat.eximpe.com/pg/payments/PR6938527534/documents/' \
  -H 'X-Client-ID: <client_id>' -H 'X-Client-Secret: <client_secret>' \
  -H 'X-Merchant-ID: <sub_merchant_id>' -H 'X-API-Version: 3.0.0' \
  -F 'type=delivery_proof' \
  -F 'file=@delivery-note.pdf'
# → { "success": true, "message": "Document uploaded",
#     "data": { "ref": "a1b2c3d4-5e6f-7a8b-9c0d-1e2f3a4b5c6d", "type": "delivery_proof" } }

# 2. attach
curl -X POST 'https://api-pacb-uat.eximpe.com/pg/payments/PR6938527534/settlement-documents/' \
  -H 'X-Client-ID: <client_id>' -H 'X-Client-Secret: <client_secret>' \
  -H 'X-Merchant-ID: <sub_merchant_id>' -H 'X-API-Version: 3.0.0' \
  -H 'Content-Type: application/json' \
  -d '{ "doc_type": "delivery_proof", "ref": "a1b2c3d4-5e6f-7a8b-9c0d-1e2f3a4b5c6d" }'
```

## Response

```json
{
  "success": true,
  "message": "Document attached",
  "data": {
    "document_id": "0f7c2a1e9b4d4c8e",
    "doc_type": "delivery_proof",
    "file_name": "delivery-note.pdf"
  }
}
```

## Attach many

B2B services takes **any number of files under `delivery_proof`**. Call this once per file — each attach returns its own `document_id`.

Attaching the same `ref` under the same `doc_type` twice does not create a second row; you get the existing one back. That makes a retried call safe.

## When it is refused

Every refusal is a `400` in the standard envelope:

```json
{
  "success": false,
  "error": {
    "code": "ERR_B2B_SETTLEMENT_003",
    "message": "Documents can only be uploaded after the payment is settled.",
    "details": "Documents can only be uploaded after the payment is settled."
  }
}
```

| Cause | `code` | What to do |
|---|---|---|
| The payment is not settled | `ERR_B2B_SETTLEMENT_003` | Wait for [`PAYMENT_SETTLED`](/api-reference/v3/webhooks/payment-settled). Post-settlement documents only exist after settlement. |
| The set has already been submitted | `ERR_B2B_SETTLEMENT_002` | It is locked. Nothing further can be attached or deleted. |
| `doc_type` is not `delivery_proof` | `40359` | That is the only type B2B services defines. `details` is keyed by field: `{"doc_type": "Unknown document type."}`. |
| The `ref` is unknown | `ERR_B2B_SETTLEMENT_001` | A `ref` that is not your own reads as unknown. Upload the file under the calling merchant — PSPs must send `X-Merchant-ID` naming the settling sub-merchant. |
| The payment is not a B2B-services payment | `40360` | B2B goods has no partner-API settlement path. |

<Note>
  **PSP callers must send `X-Merchant-ID`** on both calls, naming the settling sub-merchant. The upload is scoped to the merchant that made it, and the attach resolves the `ref` against that same merchant — mismatch them and the `ref` reads as unknown.
</Note>
