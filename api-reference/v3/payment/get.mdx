## Overview

Returns the full record of one payment: the order it belongs to, the settlement that paid it out, any refunds against it, and details of the method the buyer used. Take the `payment_id` from [List Payments](/api-reference/v3/payment/list) or from a payment webhook.

<Note>
  **PSPs can fetch any payment they can act for**: their own, or any sub-merchant's. `X-Merchant-ID` is not needed here, and does not narrow the lookup.
</Note>

## Payment status

`status` is the payment's status as recorded: `pending`, `captured` or `failed`.

<Note>
  **A pending payment that has expired still reads `pending` here.** [List Payments](/api-reference/v3/payment/list) shows the same payment as `failed`. Treat a `pending` payment whose order has passed its expiry as failed.
</Note>

`order.status` is the order's status, not the payment's: `payment_pending`, `payment_successful` or `failed`. An order can have several payments, one per attempt, so a `failed` payment can belong to a `payment_successful` order.

## Response Fields

- `order.amount` is a decimal string with two places, e.g. `"1500.00"`. The same applies to `settlement.settlement_amount` and `refund[].refund_amount`. Parse them as decimals, never as floats.
- `settlement` is `null` until the payment is settled.
- `refund` lists refunds against the payment, newest first, and is `[]` when there are none. `refund_status` is one of `initiated`, `processing`, `refunded`, `failed`, `reversed`, `on_hold` or `bank_rejected_refund`.
- `collection_mode` is how the payment was collected: `hosted_payment`, `payment_link` or `s2s`.
- `mop_type` and `order.opted_mop_type` are lowercase, e.g. `upi` or `credit_card`. `opted_mop_type` is the method chosen when the order was created; `mop_type` is the one the buyer actually used.
- `mop_detail` depends on `mop_type`:

| `mop_type` | `mop_detail` |
|---|---|
| `upi` | `vpa`, `upi_instrument`, `upi_app` |
| `credit_card`, `debit_card` | `card_last_4_digits`, `card_holder_name`, `card_issuer_country`, `card_issuer_bank` |
| `net_banking` | `bank_ref_num`, `acq_id` |
| `qr`, or any other method | `null` |

Any field inside `mop_detail` can be `null` when the payment provider did not return it.

- For a UPI payment, `upi_instrument` is what funded it, lowercase: `upi` (bank account), `upi_cc` (credit card on UPI), `upi_cl` (credit line on UPI), `upi_ppi` (wallet), `upi_si` (UPI standing instruction) or `upi_si_ppi` (standing instruction from a wallet). `null` means the provider did not report the instrument. It does not mean plain UPI.
- `upi_app` is the UPI app the payer used, e.g. `PhonePe`, worked out from the handle of their VPA. It is `null` when the handle is not one we recognise.

- `created_at`, `payment_completed_at`, `order.created_at`, and the timestamps under `settlement` and `refund`, are UTC with microseconds, e.g. `2026-10-15T06:44:13.414209Z`.

## Errors

A payment ID that does not exist, or belongs to a merchant you cannot act for, returns `404`:

```json
{
  "success": false,
  "error": {
    "code": "ERR_PAYMENT_005",
    "message": "Payment not found",
    "details": {
      "payment_id": "Payment not found"
    }
  }
}
```

<Info>
  The response is the same whatever `X-API-Version` you send. v1, v2 and v3 integrations share this endpoint and its response.
</Info>
