## Overview

A payment form is a page EximPe hosts for you at `/pay/<url_slug>/`. You create it once, share the URL, and every payer who opens it fills in their own details, gets their own order, and pays. There is no per-payer API call.

```bash
curl -X POST 'https://api-pacb-uat.eximpe.com/pg/forms/' \
  -H 'X-Client-ID: <client_id>' -H 'X-Client-Secret: <client_secret>' \
  -H 'X-Merchant-ID: <sub_merchant_id>' -H 'X-API-Version: 3.0.0' \
  -H 'Content-Type: application/json' \
  -d '{
    "url_slug": "spring-workshop",
    "payment_for": "Spring Workshop Ticket",
    "type_of_goods": "service",
    "currency": "INR",
    "is_fixed_amount": true,
    "amount_cents": 250000,
    "collect_name": true,
    "collect_email": true,
    "collect_phone": true
  }'
```

The response carries `form_url` — the link to share — and `form_id`, which every other Payment Forms endpoint takes in its path.

## The three decisions

<ParamField body="url_slug" type="string" required>
  The public path. `spring-workshop` is served at `/pay/spring-workshop/`.

  Letters, digits and hyphens only. It is lower-cased before it is stored, and it is unique across **every merchant on EximPe** — not just yours. It cannot be changed after the form exists, and deactivating a form does not release it.
</ParamField>

<Warning>
  **Every segment of the slug is checked against a reserved list**, and one reserved segment refuses the whole slug — so `my-payment-form` is rejected twice over, for `payment` and for `form`. The list: `admin`, `api`, `login`, `logout`, `static`, `media`, `health`, `config`, `internal`, `dashboard`, `merchant`, `root`, `support`, `pay`, `form`, `forms`, `public`, `import`, `payment`, `checkout`, `callback`, `csp-report`. A profanity filter runs over the slug and its segments as well. Both refusals read `This URL slug is not allowed. Please choose a different one.`

  Name the thing being paid for, not the mechanism: `spring-workshop`, `acme-membership-2026`.
</Warning>

<ParamField body="is_fixed_amount" type="boolean" default="true">
  `true` charges everyone `amount_cents`, which is then required. `false` lets the payer type an amount, up to ten million rupees, and `amount_cents` is ignored.

  `amount_cents` is in the minor unit — paise for INR, so `250000` is ₹2,500. You may send `amount` in rupees instead.
</ParamField>

<Warning>
  **Send `amount` or `amount_cents`, never both.** `amount_cents` is honoured only when `amount` is absent from the body; if both are present it is silently discarded — including when `amount` is `null`, which then refuses the call with `Amount is required for fixed amount forms`. `amount`, in rupees, is the key to prefer: it is what the response gives back.
</Warning>

<ParamField body="collect_name / collect_email / collect_phone" type="boolean" default="true">
  Which payer details a submission is **refused without**. All three default to `true`.

  They do not control the layout. The hosted page always shows name, email, phone and postal code, whatever these flags say; the flags are the server-side check applied when the payer submits. There is no way to add a field to the page or take one off it.
</ParamField>

<Note>
  **The page collects name, email, phone and postal code — nothing else.** It has no PAN field and no date-of-birth field, and of an address it keeps only the postal code.
</Note>

## Goods and HS codes

`type_of_goods` is required, matched case-insensitively, and stored lower-case: `goods`, `physical_goods`, `digital_goods` or `service`.

<Warning>
  **`physical_goods` needs an `hs_code`.** And whenever you send an HS code — for any `type_of_goods` — it is checked against EximPe's HS master here, at create time. That is deliberate: a bad code saved now would otherwise fail every payer's submission later.
</Warning>

## Branding

`logo` is a file, so a request that carries one must be `multipart/form-data`; everything else is happy as JSON. Read the logo back as `logo_url` — a pre-signed, time-limited URL, so fetch it when you need it rather than storing it.

`primary_color` is a six-digit hex code (`#1E40AF`). `template_style` picks the summary-pane layout, `template1` or `template2`. `business_name_type` chooses which of your two registered names payers see — `trade_name` or `legal_name` — and the name itself is read live from your KYC record, so a correction there reaches forms you already created.

## Pre-selecting a payment method

`preferred_mop_type` pre-selects a method on the hosted page. Send it upper-case.

<Warning>
  **Only six values can actually be paid**: `CREDIT_CARD`, `DEBIT_CARD`, `UPI`, `NET_BANKING`, `WALLET` and `QR`.

  Create accepts a wider set of method names than the payment step does. A form saved with anything outside those six is created without complaint and then refuses **every** payer submission — the form looks healthy over the API and collects nothing. Send one of the six, or leave `preferred_mop_type` out.
</Warning>

## What comes back

The `201` body is the standard `{success, message, data}` envelope. `data` is deliberately narrower than what you sent: `description`, `type_of_goods`, `hs_code`, `success_url`, `fail_url`, `valid_from`, the `collect_*` flags, `auto_generate_invoice`, `allowed_payment_methods` and `preferred_mop_type` are all stored, but not echoed back. `amount` comes back in rupees, not `amount_cents`.

<Note>
  **`form_id` is the form's own ID (`PF` + ten digits)** — not the optional `form_id` tracking column on the model, which the Partner API does not let you set.
</Note>

<Note>
  **PSP callers must send `X-Merchant-ID`** naming the sub-merchant that collects, and the form then belongs to that sub-merchant, not to the PSP. Direct merchants leave it out. A missing or unknown header here is a `401` — `ERR_AUTH_000` or `ERR_AUTH_001` — even though your own credentials were fine.
</Note>

<Note>
  **The lane check guards creation only.** Creating a form on an account that is not set up for payment forms is a `403 ERR_AUTH_005`; if the entitlement is withdrawn later, forms already created keep listing, updating and collecting. Deactivate them yourself if they should stop.
</Note>

## Validity, and what the payer sees

`valid_from` and `valid_until` bound the window in which the form takes money. Together with `is_active` they decide `is_valid`.

<Note>
  **An out-of-window form `404`s the payer.** `/pay/<url_slug>/` answers `404` before `valid_from` and after `valid_until`, while the form itself stays listable, retrievable and updatable over the API with `is_valid: false`. That asymmetry is what makes `valid_until` the way to pause a form: move the date and the page comes back. [Deactivating](/api-reference/v3/payment-form/deactivate) cannot be undone.
</Note>

<Note>
  **A deactivated merchant account `404`s the page too.** The public page is gated on the collecting account being active as well as the form, so if the account is closed or suspended every one of its forms stops serving at once — with no change to the forms themselves.
</Note>

## Limits

<Note>
  **The ten-million-rupee ceiling binds the payer, not you.** An amount a payer types into a variable-amount form is capped at ₹10,000,000 and refused above it. The same ceiling is *not* checked on `amount_cents` when the form is created or updated, so a fixed-amount form can be saved well above it. Keep your own bound on `amount_cents` rather than relying on a `400`.
</Note>

<Note>
  **There is no rate limit on the Payment Forms endpoints.** This viewset opts out of the Partner API's throttles, so nothing here answers `429`. Treat that as a current property of the implementation, not a commitment — it is not a reason to poll hard.
</Note>
