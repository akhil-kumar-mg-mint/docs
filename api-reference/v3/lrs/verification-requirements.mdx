openapi: 'GET /pg/payments/{payment_id}/verification/'
---

## Overview

Returns the verification requirements for one payment: every field and document its checklist calls for, which are already satisfied, and which are still outstanding.

The checklist is chosen by two facts on the order — its **business model** and its **purpose code**. Until both are declared no checklist claims the payment, and this endpoint asks for them instead.

The [`LRS_VERIFICATION_NEEDED`](/api-reference/v3/webhooks/lrs-verification-needed) webhook lists what a payment is **missing**. This returns the **whole** set. Both describe the same items in the same shape, from the same read — an entry here is an entry there plus `satisfied` and `provided`.

<Note>
  **Do not hardcode the field list.** Requirements are configuration, not code, and are revised as the underlying regulatory matrix is. Reading them from here means a revision reaches your integration without a release on your side.
</Note>

## When to use it

<Steps>
  <Step title="You missed an event">
    Webhooks get lost, retried, or arrive mid-deploy. This endpoint is authoritative and idempotent — call it any time. It is also the only place that reports `settlement_status`, which tells you whether sending anything is still possible.
  </Step>
  <Step title="You need the whole set">
    The event lists what is outstanding. Call this when you also need what is already satisfied — reconciling your record against ours, or rendering a progress view.
  </Step>
  <Step title="You are resuming">
    A payer supplied three documents last week and two today. Call this to see where the payment stands before asking for anything.
  </Step>
  <Step title="You are building the form">
    `fields` and `documents` describe the whole set, satisfied or not, with a `message` per item safe to show a payer. Filter on `satisfied` for what is still owed.
  </Step>
</Steps>

## Reading the response

### The payment

<ParamField path="payment_id" type="string" required>
  The payment. It is also the `payment_id` in this endpoint's own path.
</ParamField>

<ParamField path="order_id" type="string" required>
  The order the payment belongs to. Every verification event names it under this key too.
</ParamField>

<ParamField path="settlement_status" type="string" required>
  **The payment's own state — not a roll-up of the checklist.** This is the one thing an item list cannot tell you, and it is why this endpoint is worth calling when an event was missed: it says whether acting on the list is still possible at all.

  | Value | What it means for you |
  |---|---|
  | `ACTION_REQUIRED` | The payment is waiting on you. Send what is outstanding. |
  | `INFO_PENDING` | The same, earlier in the flow — nothing has been filed yet. |
  | `UNDER_REVIEW` | Filed and with EximPe. **Sending is closed** — see below. This value does not change when EximPe approves: read [`review.review_state`](#the-review) for the decision. |
  | `READY_FOR_SETTLEMENT` · `SETTLED` | Past verification. Sending is closed. |
  | `EXPIRED` · `REJECTED` · `ON_HOLD` | The payment did not proceed. Nothing you send reopens it. |

  A payment can also read `NOT_APPLICABLE`, `PAYMENT_PENDING`, `PAYMENT_FAILED` or `SETTLEMENT_ERROR` — states in which no verification is being asked of you.

  Once the verification has been **filed**, sending closes: a `POST` to this path is refused. A rejected or fully refunded payment refuses sends too. Read this key before you send.
</ParamField>

<ParamField path="business_model" type="string | null" required>
  `B2B` or `B2C`, or `null` while nothing has declared it.
</ParamField>

<ParamField path="purpose_code" type="string | null" required>
  The FEMA/FETERS purpose code the order settles under, or `null` while none is declared.
</ParamField>

### The review

A classified payment also carries a `review` object — what EximPe decided about the verification, in words that do not depend on which flow the payment is in. It is the one place that tells an approved payment from one still waiting, because both keep `settlement_status: "UNDER_REVIEW"`.

<ParamField path="review.review_state" type="string" required>
  | Value | What it means |
  |---|---|
  | `FRESH` | Nothing has been filed. |
  | `UNDER_REVIEW` | Filed and waiting for EximPe review. |
  | `CHANGES_REQUESTED` | EximPe sent it back. The payment is open again. |
  | `APPROVED` | EximPe approved it. `settlement_status` stays `UNDER_REVIEW` until the payment settles. |
  | `REJECTED` | EximPe rejected it. Terminal. |
</ParamField>

<ParamField path="review.rejection_reason" type="string">
  The reviewer's overall comment on a send-back or rejection. An empty string when there is none.
</ParamField>

<ParamField path="review.reviewed_at" type="string | null">
  When EximPe last decided, as an ISO timestamp, or `null`.
</ParamField>

<ParamField path="review.documents" type="array">
  One entry per stored document: `doc_type`, `doc_status` (`PENDING` · `VERIFIED` · `REJECTED`) and the reviewer's `rejection_comment` for that file.
</ParamField>

<Note>
  An unclassified payment has no checklist and no review, so the `review` key is absent from that response.
</Note>

### The items

There is one list per kind, holding the whole set. There is no separate "missing" array — what is still owed is a filter:

```js
const outstanding = data.fields.filter(f => !f.satisfied)
```

Every entry in `fields` and `documents` carries `code`, `message`, `satisfied` and `provided`. The remaining keys appear **only when they apply**, so their absence is meaningful: no `optional` key means the item is required, no `waivable` key means it cannot be waived.

<ParamField path="code" type="string" required>
  The identifier you send the answer back under — as a key in `fields`, or as a document's `code`. See [Submit Verification Details](/api-reference/v3/lrs/submit-verification-details).
</ParamField>

<ParamField path="message" type="string" required>
  A human-readable description of the item, safe to render to a payer. On `buyer_declaration` it is the wording the payer must be shown before affirming.

  The same key on a [submit-failure event](/api-reference/v3/webhooks/lrs-verification-needed#after-a-submit-that-did-not-pass) carries a sentence about what went wrong instead. One key, always the plainest thing there is to say about the item.
</ParamField>

<ParamField path="satisfied" type="boolean" required>
  Whether this item still blocks completion. `false` is what "missing" means.

  An `optional` item is satisfied from the very first response, and a conditional item whose condition does not hold is satisfied vacuously. Neither blocks completion.
</ParamField>

<ParamField path="provided" type="boolean" required>
  Whether a value actually exists — you sent it, or we already held it. Read alongside `satisfied`:

  | `satisfied` | `provided` | Means |
  |---|---|---|
  | `false` | `false` | Owed. Send it. |
  | `true` | `true` | Done. |
  | `true` | `false` | Nothing owed, nothing sent — an optional item, or a conditional one that does not apply to this payment. |

  That last row is why `satisfied` alone is not enough. To offer optionals to a payer as well as chase what is owed, widen the filter:

  ```js
  const offerable = data.documents.filter(
    d => !d.satisfied || (d.optional && !d.provided)
  )
  ```
</ParamField>

<ParamField path="optional" type="boolean">
  Present, and always `true`, on items that never block completion. Absent on required items — there is no `"optional": false`.

  An optional item is listed until you supply it, because an optional document nobody is told about is one nobody sends.
</ParamField>

<ParamField path="condition" type="string">
  Present on conditional items, naming the case that makes them owed.

  | Value | Owed when |
  |---|---|
  | `PAYING_FOR_SOMEONE_ELSE` | A person other than the remitter is on the remittance. |
  | `PASSENGER_DETAILS_LEVEL` | Your account [collects traveller details](/api-reference/v3/lrs/submit-verification-details#verification-level) on travel payments. |
  | `GOODS_PURPOSE_CODE` | The order's purpose code is a goods code. |

  While the condition cannot yet be evaluated — no person has been sent — the item reads `satisfied: true`, `provided: false`. It is still listed, so you know it exists.
</ParamField>

<ParamField path="waivable" type="boolean">
  Present, and always `true`, on documents you may discharge with a `waiver_reason` instead of a file.

  A waivable document stays `satisfied: false` until you either upload it or record a waiver. The waiver is yours to declare, not ours to assume.
</ParamField>

<ParamField path="one_of" type="string">
  A group name. Items sharing a group substitute for each other: send any one and the whole group clears.

  No checklist uses this today — where two documents are interchangeable the checklist gives them a single code instead (`student_id_or_visa`). The key is part of the contract because a future revision may split such a pair, and an integration that reads it will absorb that without a release.
</ParamField>

### What was sent under a document code

An entry in `documents` carries three more keys once a row exists for that code. They are absent while the slot is untouched, so their presence is itself the signal that something is held. `ref` needs a file; `doc_status` does not — a slot discharged by a waiver is a stored row with no file, and reads `PENDING` with no `ref`:

```json
{
  "code": "offer_letter",
  "message": "Letter of admission from the institution",
  "satisfied": false,
  "provided": true,
  "ref": "6757940683",
  "doc_status": "REJECTED",
  "rejection_reason": "Letter is for the wrong intake term."
}
```

<ParamField path="ref" type="string">
  The upload identifier [Upload Document](/api-reference/v3/lrs/upload-document) returned for the file held in this slot — the same `ref` you submitted. Present only once a file has been sent under this code: a replacement upload supersedes the older row, so this always names the current file.
</ParamField>

<ParamField path="doc_status" type="string">
  Where this one document stands: `PENDING` (not reviewed individually), `VERIFIED` (accepted) or `REJECTED` (refused — replace it). Present once a row exists for the slot, including one discharged by a waiver — that row has no file, so it reads `PENDING` and carries no `ref`.

  It is not a synonym for `satisfied`. `satisfied` says whether the checklist item blocks completion; `doc_status` says what a reviewer made of the file.
</ParamField>

<ParamField path="rejection_reason" type="string">
  The reviewer's text about **this document**, present only when they left some. The sentence to show a payer when you ask for a replacement file.
</ParamField>

<Note>
  **These three are LRS-only, and documents-only.** Entries in `fields` never carry them — a field has no file and no reviewer mark — and the B2B goods and B2B services responses are unchanged. The same three keys appear on document entries in [`LRS_VERIFICATION_NEEDED`](/api-reference/v3/webhooks/lrs-verification-needed) and [`VERIFICATION_STATUS`](/api-reference/v3/webhooks/verification-status), with the same meanings.
</Note>

## No rolled-up `status`

This response has no `complete` / `incomplete` status. "Every box is ticked" is not "the payment passed": a payment can be complete on its checklist and still be refused at verification (a PAN that will not verify, a sender who is not the account holder, a credit that does not cover the amount). The `POST` on this URL also returns a `status`, with a different meaning.

Fold your own roll-up when you want one, against a definition you chose:

```js
const complete = [...data.fields, ...data.documents].every(i => i.satisfied)
```

For where the payment actually stands, read `settlement_status`, the [submit response](/api-reference/v3/lrs/submit-verification-details#the-response), or [`LRS_VERIFICATION_NEEDED`](/api-reference/v3/webhooks/lrs-verification-needed).

<Note>
  **Nothing is re-run when you call this.** A `GET` never verifies a PAN, posts to an LRS counter or moves a payment; it reports the requirement set and what has been collected against it.
</Note>

## Errors

Every refusal is a `400`; the code inside the envelope is what tells them apart.

| `error.code` | When |
|---|---|
| `40360` | No such payment for this merchant. The same answer whether it does not exist or belongs to someone else, so the endpoint never confirms another merchant's payment id. |
| `40359` | The payment is classified, but no checklist covers that business model and purpose code — there is nothing to report. An **unclassified** payment is not this case: it answers `200`, asking for the two classifying facts. |

## What each checklist asks for

The exact set is always what this endpoint returns — this is a summary, and a revision lands there before it lands in any table.

### Every checklist starts here

Buyer and invoice basics, read straight off the order:

`buyer_name` · `buyer_address_line_1` · `buyer_city` · `buyer_state` · `buyer_postal_code` · `buyer_email` · `buyer_phone` · `invoice_number` · `invoice_date`

On the LRS and B2C checklists `buyer_address_line_1`, `buyer_city` and `buyer_state` are `optional`: they are listed, they never block completion, and a blank value sent for one is ignored. `buyer_postal_code` stays required. The B2B checklists still require all of them.

The light B2C set (`S0101`, `S0802`, `S0301`) asks for those nine fields and no remitter identity, then adds:

| Code | Asks for |
|---|---|
| `invoice_amount` | Invoice total in INR, as stated on the invoice |
| `declaration` | The declaration the payer affirms: the purchase is genuine and the invoice is accurate |
| `hs_code` | HS code of the goods. Owed only when the purpose code is a physical-goods code |
| `invoice` (document) | Optional |

### LRS checklists

`S0305`, `S1107`, `S0303`, `S0304` and `S0306` add the remitter's verified identity, the declaration and the amounts:

| Code | Asks for |
|---|---|
| `remitter_pan` | Remitter PAN |
| `remitter_dob` | Remitter date of birth, as per PAN |
| `buyer_declaration` | One affirmation covering all three LRS claims — send `true` once the payer has affirmed the wording in `message` |
| `amount_to_be_settled` | The amount to settle for this payment, in INR |
| `persons` | The people on the remittance. Education: exactly one, the student. Travel: every traveller, but only if your account collects traveller details. See [Persons](/api-reference/v3/lrs/submit-verification-details#persons) |

<Note>
  **The remitter's name is not on this list, and neither is the TCS.** The name comes from [Verify PAN](/api-reference/v3/lrs/verify-pan), which you call before you can quote or submit — it is already on file under the PAN you declare. The TCS is the figure we quote against the payer's year-to-date LRS usage; [Quote LRS Amount](/api-reference/v3/lrs/quote) tells you what to collect, and the credit is checked against it. Neither is yours to re-declare here.
</Note>

If `amount_to_be_settled` is not on your checklist, do not send it.

Documents, per purpose code:

| Document code | `S0305` | `S1107` | `S0303` · `S0304` · `S0306` |
|---|:---:|:---:|:---:|
| `offer_letter` — letter of admission | required | required | — |
| `passport` — student's passport | required | — | — |
| `student_id_or_visa` — student visa **or** university ID card | required | — | — |
| `student_id` — university ID card | — | required | — |
| `fee_invoice` | optional | optional | — |
| `relationship_declaration` | conditional | conditional | — |

<Note>
  **`student_id_or_visa` is one code that accepts either document.** Upload a visa or a university ID card under this single code — there is no separate `student_visa` or `university_id_card` to send, and no alternative group to reconcile. `S1107` has no travel leg, so no visa exists and the university ID stands alone as `student_id`.
</Note>

### B2B checklists

| Code | Extra fields | Documents |
|---|---|---|
| `S0101` — goods | `invoice_amount`, `declaration`, `hs_code` and `iec` | `invoice` |
| `S0802` · `S0803` · `S1005` · `S1009` · `S1010` · `S1013` · `S1015` · `S1016` · `S1017` · `S1105` · `S1106` — services | `invoice_amount` and `declaration` | `invoice` |

## The requirement set can grow

Answering one requirement can reveal another. Sending a person other than the remitter flips `relationship_declaration` to `satisfied: false`, because it is only owed in that case. If your account collects traveller details on travel payments, `persons` is owed on them.

This is expected. Re-read `fields` and `documents` after every write rather than assuming the list you started with is final.
