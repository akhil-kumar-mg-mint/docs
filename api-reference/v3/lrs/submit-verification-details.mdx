## Overview

An LRS payment answers a longer list than an ordinary one: the remitter's verified identity, the LRS declarations, the TCS collected, and a set of documents that depends on the purpose code. This page is that list, and what happens once it is complete.

<Note>
  **Same endpoint as [Submit Payment Verification Details](/api-reference/v3/payment/submit-verification-details).** One URL answers every verification ask — `fields`, `documents`, partial sends and the response shape all work identically. Only what a payment is *asked for* differs, and that is what this page covers. If you do not handle LRS payments, the other page is all you need.
</Note>

Send details keyed by the same codes that [Get Verification Requirements](/api-reference/v3/lrs/verification-requirements) and the [`LRS_VERIFICATION_NEEDED`](/api-reference/v3/webhooks/lrs-verification-needed) webhook use.

There is nothing to map between them — every one of those places names an item under `code`:

| Where you read it | What you do with it |
|---|---|
| the `GET`'s `fields[].code` | the key you put in `fields` |
| the `GET`'s `documents[].code` | the `code` you put in `documents` |
| the webhook's `action_required_fields[].code` | the key you put in `fields` |
| the webhook's `action_required_documents[].code` | the `code` you put in `documents` |

**JSON only.** `fields` is an object; `documents` is a list of `{code, ref}` naming files uploaded earlier through [Upload Document](/api-reference/v3/lrs/upload-document). Files are never posted to this endpoint.

## The loop

<Steps>
  <Step title="An event arrives">
    [`LRS_VERIFICATION_NEEDED`](/api-reference/v3/webhooks/lrs-verification-needed) lists what the payment owes — each entry a code and a sentence.
  </Step>
  <Step title="You upload any files">
    [Upload Document](/api-reference/v3/lrs/upload-document) returns a `ref` per file. Upload each as it arrives; nothing has to be held back.
  </Step>
  <Step title="You send what you have">
    Fields as a map, documents as `{code, ref}`. Partial is fine — later sends merge over earlier ones.
  </Step>
  <Step title="You read where the payment stands">
    The response says both: a `status`, and `outstanding` — the codes still owed after this write.
  </Step>
</Steps>

## The body depends on the checklist

There is one endpoint and one envelope — `fields`, `documents`, `persons`, `finalize` — but **what belongs inside them is decided by the payment's checklist**, not by you. That checklist comes from the order's business model and purpose code together.

You never have to work out which set applies: `GET` the same path and it tells you, or read the codes off the event.

**Declaring an LRS purpose code is what makes a payment an LRS one.** Send `business_model` and `purpose_code` together in `fields` — see [Submit Payment Verification Details](/api-reference/v3/payment/submit-verification-details#which-codes-to-send) for the rules that govern the pair — and if the code is one of the five below, the payment switches to [`LRS_VERIFICATION_NEEDED`](/api-reference/v3/webhooks/lrs-verification-needed) and starts being asked for everything on this page.

The pair may ride in the same call as the rest.

The three travel codes take an identical body. They differ in what the remittance is *for* — other travel, medical treatment, pilgrimage — not in what you must collect. Travel asks for **no documents**, and asks for [`persons`](#persons) only when your account [collects traveller details](#verification-level).

**Education is always asked for one person: the student.** The parent or sponsor who pays is not a second entry — they are identified by `remitter_pan` and `remitter_dob` in `fields`. Sending a student who is not the remitter is what makes `relationship_declaration` owed. If the remitter is the student, send only `[{ "is_remitter": true }]` (with a `passport_number` on `S0305`) and it drops out.

**The remitter name and TCS are not fields;** the name comes from [Verify PAN](/api-reference/v3/lrs/verify-pan) and the TCS from the quote.

### What differs, and what does not

| | `S0305` | `S1107` | `S0303` · `S0304` · `S0306` |
|---|:---:|:---:|:---:|
| Buyer and invoice fields | same | same | same |
| Buyer address line 1, city and state | optional | optional | optional |
| Remitter identity, declaration, `amount_to_be_settled` | same | same | same |
| `persons` | exactly one person: the student | exactly one person: the student | only if your account collects traveller details: every traveller, the remitter included |
| Passport number on each person | required, the remitter included | not asked for | required |
| Required documents | `offer_letter`, `passport`, `student_id_or_visa` | `offer_letter`, `student_id` | none |
| Optional documents | `fee_invoice` | `fee_invoice` | — |
| Conditional document | `relationship_declaration` | `relationship_declaration` | — |

**The address lines are optional here; the PIN code is not.** `buyer_address_line_1`, `buyer_city` and `buyer_state` never block completion on an LRS checklist, and a blank value sent for one is ignored rather than refused. The body examples above include them for completeness. `buyer_postal_code` is still required.

<Warning>
  **Do not branch on the purpose code in your own integration.** Read the checklist instead. The codes above are what the matrix asks for today; it is configuration, and a revision reaches you through the API without a release on your side — but only if you are reading it rather than reproducing it.
</Warning>

## Values

Field values are strings, numbers or booleans.

| Kind | Send |
|---|---|
| Dates (`invoice_date`, `remitter_dob`, and `dob` on a person) | `YYYY-MM-DD` |
| Amounts (`amount_to_be_settled`) | A decimal string in rupees, e.g. `"150000.00"` |
| `buyer_declaration` | `true`, once the payer has affirmed the wording in the item's `message` |
| `business_model` | `B2B` or `B2C`. Case-insensitive. |
| `purpose_code` | A FEMA/FETERS code the account this payment **settles to** is allow-listed for, e.g. `S0305`. Case-insensitive. For a PSP that is the sub-merchant on the order, not the calling credential. |

**An unknown key is a `400`, not a silent drop.**

Omit a key rather than sending a blank value. A declaration must be a JSON boolean — the string `"true"` is refused with `ERR_DECLARATION_001`, `Declaration must be true or false.`.

### Documents

Each entry names one code and **exactly one** of `ref` or `waiver_reason`. Sending both, or neither, is a `400`.

| Key | |
|---|---|
| `code` | The checklist code this file answers — `offer_letter`, `passport`, `student_id_or_visa`, … |
| `ref` | A `ref` returned by [Upload Document](/api-reference/v3/lrs/upload-document). |
| `waiver_reason` | Why the document is not being supplied. Only accepted on items whose `waivable` is `true`. |

Sending the same code twice in one call is a `400`. Sending it again in a **later** call is fine — the newer ref or waiver replaces the earlier row.

## Persons

`persons` is a top-level list in the request body, beside `fields` and `documents` — not an entry inside `fields`. Each entry describes one person on the remittance.

```json
{
  "persons": [
    { "is_remitter": true, "nationality": "IN", "passport_number": "Z1234567" },
    { "is_remitter": false, "name": "Meera Kumar", "relation": "SPOUSE", "nationality": "IN", "passport_number": "Y7654321" }
  ]
}
```

| Key | |
|---|---|
| `is_remitter` | Required. `true` for the person paying. At most one entry may be the remitter. |
| `name` | Required for everyone who is not the remitter. Omit it for the remitter — the name comes from [Verify PAN](/api-reference/v3/lrs/verify-pan). |
| `relation` | Required for everyone who is not the remitter: **that person's relation to the remitter**, so a student paid for by a parent is `CHILD`. `PARENT` · `GUARDIAN` · `SPOUSE` · `SIBLING` · `CHILD` · `OTHER`. Not allowed on the remitter's own entry — mark the remitter with `is_remitter`, not a relation. |
| `dob` | `YYYY-MM-DD`. Required for an education student who is not the remitter. Not in the future, and not more than 120 years ago. |
| `nationality` | Two-letter country code, e.g. `IN`. Required for every traveller on a travel code. |
| `passport_number` | Letters, digits and dashes, up to 32 characters. Required for every traveller, and for the one person on `S0305`. Not asked for on `S1107`: leave it out. Self-declared and never checked against a register. |

Sending `persons` again replaces the list; the newest send wins. Nothing about a person is ever returned to you — the [`GET`](/api-reference/v3/lrs/verification-requirements) reports only whether `persons` is `satisfied` and `provided`.

### Verification level

Your EximPe contact configures whether travel payments collect traveller details; the checklist's `persons` item tells you.

### Person errors

A list that breaks one of these rules is refused as a whole, and each carries a code of its own:

| `error.code` | Message | When |
|---|---|---|
| `ERR_LRS_MERCHANT_016` | Select the nationality of every passenger. | A travel entry has no `nationality`. |
| `ERR_LRS_MERCHANT_017` | Enter the passport number of every person. | A travel entry, or the `S0305` student, has no `passport_number`. |
| `ERR_LRS_MERCHANT_018` | Enter the date of birth of the person the remittance is for. | An education student who is not the remitter has no `dob`. |
| `ERR_LRS_MERCHANT_019` | Exactly one person is required for this purpose code. | An education send that lists more than one person. |

The rules on a single entry answer under `40359`, with the message in `details`:

| Message | When |
|---|---|
| `The remitter's own entry cannot have a relation.` | The entry with `is_remitter: true` carries a `relation`. |
| `Enter the name and relation of every other person.` | An entry that is not the remitter is missing its `name` or `relation`. |
| `Only one person can be marked as the remitter.` | More than one entry has `is_remitter: true`. |
| Format errors | Name the field in `details`; fix the value and send again. |

## Linking a top-up

When a credit is a further payment against an earlier one — the buyer was short, or paid the TCS separately — say so on the call that files:

```json
{
  "fields": { "…": "…" },
  "linked_payment_id": "PR6938527534",
  "reason": "REMAINING_AMOUNT"
}
```

| Key | |
|---|---|
| `linked_payment_id` | The earlier payment this one tops up. Resolved against your own payments; a link we cannot resolve is refused. |
| `reason` | `REMAINING_AMOUNT` — covering a shortfall on the amount to be settled. `TCS_PAYMENT` — paying the TCS separately. An audit label on the link. |

**A `reason` without a `linked_payment_id` is a `400`.** The reverse is fine: a link with no reason is just an unlabelled link.

Like `finalize`, these describe **the send**, not the payment. They are read by the call that actually files, and a call that only saves carries them nowhere — so send them with the call that completes the set.

## Partial sends are merged

Send three fields today and two tomorrow and you have sent five. Nothing you sent earlier is wiped by a later call, and a field's newest value wins.

**`finalize` defaults to `true`.** It applies only to a **complete** set and never forces an incomplete one through, so a partial send is accepted either way — you do not have to set it. Pass `finalize: false` only to save without filing.

<Warning>
  Once you have filed, sending is closed.
</Warning>

## The response

Three keys, whatever you sent — and a fourth, `refusal`, on the one response that has something more to say: a complete set that did not pass verification.

<CodeGroup>

```json Still owed
{
  "success": true,
  "message": "Verification details received",
  "data": {
    "payment_id": "PR6938527534",
    "status": "incomplete",
    "outstanding": ["remitter_pan", "remitter_dob", "offer_letter"]
  }
}
```

```json Complete and filed
{
  "success": true,
  "message": "Verification details received",
  "data": {
    "payment_id": "PR6938527534",
    "status": "in_review",
    "outstanding": []
  }
}
```

```json Complete, but verification did not pass it
{
  "success": true,
  "message": "Verification details received",
  "data": {
    "payment_id": "PR6938527534",
    "status": "action_required",
    "outstanding": [],
    "refusal": {
      "reason": null,
      "missing": ["outstanding"],
      "outstanding_cents": 73750
    }
  }
}
```

</CodeGroup>

<ParamField path="status" type="string" required>
  Lower-case, always one of four. The first two answer *is the checklist satisfied*; the second two answer *what happened when it was filed*, and only appear on a call that actually filed.

  | Value | What it means | What to do |
  |---|---|---|
  | `incomplete` | Something is still owed. `outstanding` names it. | Send the rest. |
  | `complete` | Nothing is outstanding, and nothing was filed — you passed `finalize: false`, or this payment's checklist is not an LRS one and is not filed for verification. | Nothing, unless you held it back. |
  | `in_review` | The set was complete, it was filed, and verification passed. The payment is with EximPe. | Nothing. |
  | `action_required` | The set was complete and filed, and verification did not pass the payment. | Read the event, fix what it names, re-send only that. |
</ParamField>

<ParamField path="outstanding" type="array" required>
  The codes still owed **after** this write — the same codes you would get by filtering the `GET` on `satisfied: false`. Empty when nothing is.

  This is the list, not a pointer to one. You do not need a second call to learn what is left.
</ParamField>

<ParamField path="refusal" type="object">
  Why verification refused a set the checklist called complete. Present **only** alongside `status: action_required` — absent from every other response, so read it as a key that may not be there rather than one that is sometimes `null`.

  Where `outstanding` says what the *checklist* still wants, this says what *verification* found. Verification only runs once the checklist is satisfied, so a refusal **always** arrives with `outstanding` empty.

  | Key | |
  |---|---|
  | `reason` | The headline verdict, upper-case — or `null` when there is no verdict beyond the items in `missing`. |
  | `missing` | What verification still wants, under the tokens listed below. These are not checklist codes. |
  | `outstanding_cents` | The shortfall still owed — principal plus MDR, GST and TCS, less what was received — in **paise**. `0` when the refusal is not about money. The amount received is the bank credit for a payment made into a virtual account, and the order amount otherwise. |

  `reason` is one of:

  | Value | What it means |
  |---|---|
  | `PURPOSE_CODE_NOT_ALLOWED` | The purpose code is not one the account this payment **settles to** is allow-listed for. For a PSP that is the sub-merchant on the order, not the calling credential. |
  | `PURPOSE_CODE_NOT_IN_REGISTRY` | The code is not an LRS purpose code at all. |
  | `PAN_NOT_VERIFIED` | The remitter's PAN is unverified, and could not be verified now. |
  | `PAN_NAME_MISMATCH` | The buyer named on the order is not the PAN's registered holder — the verification vendor's verdict. |
  | `SENDER_NAME_MISMATCH` | The same two names, judged by our own fuzzy match rather than the vendor's. |
  | `null` | No headline verdict — `missing` and `outstanding_cents` are the whole story. |

  Both name mismatches mean the buyer name and the PAN name disagree; correct whichever is wrong and send again.

  `missing` uses these tokens: `purpose_code`, `remitter.pan`, `declarations`, `primary_person`, `tcs`, `outstanding` (a shortfall), `derived_amount_credit_too_small` (the credit is too small to settle), and `documents.<type>` for each document still wanted — `documents.passport`, `documents.offer_letter`, and so on.

  The purpose-code and PAN verdicts are reached before anything else is looked at, so each carries exactly one entry in `missing` and `outstanding_cents: 0`. Only `SENDER_NAME_MISMATCH` and a `null` reason can carry a shortfall, or more than one entry.

  The same verdict also arrives as [`LRS_VERIFICATION_NEEDED`](/api-reference/v3/webhooks/lrs-verification-needed#after-a-submit-that-did-not-pass).
</ParamField>

### `outstanding` is empty and `status` is `action_required`

The checklist is satisfied; verification refused.

The verdict arrives as [`LRS_VERIFICATION_NEEDED`](/api-reference/v3/webhooks/lrs-verification-needed#after-a-submit-that-did-not-pass), same event type and same shape as any other, with the conclusion folded into the relevant entry's `message` — a shortfall's rupee figure, a PAN that would not verify, a sender who is not the account holder.

## Completion

`finalize` defaults to `true` and applies only to a **complete** set. It never forces an incomplete one through. Pass `finalize: false` only to save without filing.

When a complete set is filed it goes through verification — PAN verification, the sender-to-account-holder match, the TCS recomputation and the exactly-once LRS counter posting. `in_review` means all of that passed.

**A complete LRS set is always filed.** Sending the last outstanding item triggers verification on that same call, so the response answers `in_review` or `action_required` rather than `complete`. You only see `complete` here if you held the filing back with `finalize: false`.

A refusal is a successful `200` that reports `action_required`. If verification cannot give a verdict the call errors and nothing is lost; send the same request again.

## Errors

Every refusal is answered in the standard error envelope.

Every refusal is a `400`, whatever the reason, except a PAN check that could not run because the PAN provider is unavailable, which is a `503` (`ERR_LRS_MERCHANT_006`). The code inside the envelope is what tells refusals apart, not the status.

| `error.code` | When |
|---|---|
| `40359` | The send itself is wrong — see the codes below. Also: the payment has no checklist, and you did not send the classifying pair. |
| `40360` | No such payment for this merchant — the same answer whether it does not exist or belongs to someone else. Also: the verification has already been filed and details can no longer be changed, or the payment was rejected or fully refunded. Nothing you send reopens a rejected payment. Read `settlement_status` from the [`GET`](/api-reference/v3/lrs/verification-requirements) first. |
| `ERR_DECLARATION_001` | `buyer_declaration` was sent as something other than `true` or `false`. `details` names the field. |
| `ERR_IMPORT_VERIFICATION_003` | `business_model` and `purpose_code` do not belong together — a business buyer filing an LRS code, for example. `details.purpose_code` names the pair. |
| `ERR_LRS_MERCHANT_016` to `ERR_LRS_MERCHANT_019` | The `persons` list breaks a purpose-code rule — see [Person errors](#person-errors). |
| `ERR_LRS_MERCHANT_006` | The PAN provider could not answer (`503`). Your details are saved; retry the same call. |
| `ERR_LRS_MERCHANT_022` · `ERR_LRS_MERCHANT_024` · `ERR_LRS_MERCHANT_025` | Amount could not be derived — contact EximPe. |
| `ERR_LRS_MERCHANT_021` | If verification cannot give a verdict the call errors and nothing is lost; send the same request again. |

A `400` on the send carries `details` keyed by the offending code, so one call reports every problem at once:

```json
{
  "success": false,
  "error": {
    "code": 40359,
    "message": "Invalid LRS request.",
    "details": {
      "buyer_citty": "Not a requirement of this payment's checklist.",
      "invoice": "This is a document code; send it under 'documents'.",
      "ticket": "Sent more than once in this call."
    }
  }
}
```

| Message | Cause |
|---|---|
| `Not a requirement of this payment's checklist.` | The code is not one this checklist asks for. |
| `This is a document code; send it under 'documents'.` | A document code appeared as a key in `fields`. |
| `This is a field code; send it under 'fields'.` | The reverse. |
| `Blank value; omit the key instead.` | `null`, `""`, or whitespace. |
| `Sent more than once in this call.` | The same document code twice in one `documents` array. |
| `This document cannot be waived.` | A `waiver_reason` on an item whose `waivable` is not `true`. |
| `Unknown document ref.` | The `ref` is not one of the uploads held for the settling merchant or its parent/children. |
| `Already set on the order; it cannot be changed here.` | `business_model` or `purpose_code` after classification has landed. |

Value rules run on the send that carries the value, and name the same codes:

| Message | Cause |
|---|---|
| Format errors | Name the field in `details`; fix the value and send again. |
| `The date of birth does not match the one this PAN was verified with.` | `remitter_dob` differs from the date of birth [Verify PAN](/api-reference/v3/lrs/verify-pan) recorded for `remitter_pan`. |

Every value in a call is checked before any is written, so one bad value cannot half-apply a send. What is left for the call that **files** a complete set is verification's own verdict — see [`refusal`](#the-response) — and a call that errors because verification could not give a verdict ([`ERR_LRS_MERCHANT_021`](#errors)). Your details are still saved either way: fix the named code and re-send only that.

## Where each value goes

Most fields flow into the verification and settlement record. Two are collected but held rather than forwarded, and it is worth knowing which:

| Field | Where it goes |
|---|---|
| `buyer_name` | Held. The credit's own sender name on the order is authoritative — the LRS own-account check compares the verified PAN holder against *that*, so a submitted value must not overwrite it. |
| `purpose_code` | Held. Read from the order, which is what the settlement file uses. |

## Refunds

You can refund a payment while its verification is still open — a refund is not held back by verification.

- **A full refund closes the verification.** Sending and filing are both refused once refunds for the whole amount exist — including one that is still in progress — and the payment moves to `NOT_APPLICABLE`.
- **The LRS limit comes back when the refund completes.** When completed refunds cover the whole amount, the TCS counter and the limit that payment counted against are released, so the buyer can use them again. A partial refund leaves them as they were, and a payment that has already settled keeps its posting.
