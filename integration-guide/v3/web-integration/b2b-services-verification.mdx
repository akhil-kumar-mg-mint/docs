Money has arrived, and the payment is sitting in `ACTION_REQUIRED` — we have the funds but we do not know what the service was or who bought it. We tell you exactly what it needs, you send it, and the payment completes itself once nothing is outstanding.

<Info>
  This is the services flow — consultancy, software, professional fees, freight. Physical goods ask for an HS code and the buyer's IEC, which this flow does not collect.
</Info>

<Note>
  **PSPs send `X-Merchant-ID` on every call here**, naming the sub-merchant the payment belongs to. The purpose codes you may declare come from that sub-merchant's account, not yours.
</Note>

## There is no identity step

Worth saying before anything else, because it is what makes this flow short. **Nothing you send is verified against an external register** — no PAN, no IEC, no registration number. The buyer name is a plain field you send, checked against nothing.

Nothing has to clear before you can proceed, and there is no pre-payment step at all — no PAN to verify, no amount to quote. Everything happens after the money lands.

## Once the money lands

The payment is created as `ACTION_REQUIRED`, and a [`VERIFICATION_NEEDED`](/api-reference/v3/webhooks/verification-needed) webhook arrives naming what is outstanding, as a flat array of codes in `action_required_fields`.

<Warning>
  **Treat that first list as a nudge, not the requirement set.** The credit arrives before anything has classified the payment, so no requirement set claims it yet and the event falls back to a legacy order-field check — it can name `product_description` and `hs_code`, which this flow never asks for. Classify the payment, then read the real set from [Get Verification Requirements](/api-reference/v3/b2b/verification-requirements). A second event, `PAYMENT_DETAILS_MISSING`, follows the classifying call with the same flat list; it tells you nothing the `GET` does not, so you can ignore it.
</Warning>

From there it is one loop, repeated until nothing is outstanding:

1. **Classify the payment** if nothing has yet. A VBA credit arrives with no `business_model` or `purpose_code` on its order, so there is no checklist to read — [Get Verification Requirements](/api-reference/v3/b2b/verification-requirements) answers with those two facts as ordinary outstanding fields. Send them back under the same codes.
2. **Read what it owes** from that same endpoint. Nine buyer and invoice fields, plus the commercial invoice. Some may already be satisfied — the credit usually carries `buyer_name`.
3. **Upload the invoice** via [Upload Document](/api-reference/v3/b2b/upload-document), and keep the `ref` it returns.
4. **Send what you have** via [Submit Verification Details](/api-reference/v3/b2b/submit-verification-details) — fields as a map, documents as `{code, ref}`. Partial sends are fine; later sends merge over earlier ones.
5. Read the response: `status` says where the payment stands, and `outstanding` names what is still owed.
6. Once nothing is outstanding the set is filed, the payment moves to `in_review`, and it settles from there.

If you ever need the whole picture rather than just what changed — you missed a webhook, or you are resuming a payment someone else started — [Get Verification Requirements](/api-reference/v3/b2b/verification-requirements) returns the complete set, satisfied or not. It is idempotent, call it any time.

## Declare what the service was

Every services payment settles under one FEMA purpose code, and you pick exactly one: `S0802`, `S0803`, `S1005`, `S1009`, `S1010`, `S1013`, `S1015`, `S1016`, `S1017`, `S1105` or `S1106`, all against `business_model: "B2B"`. They share one checklist.

<Warning>
  **You can only send a code your merchant account is enabled for.** That list is set during KYC, from the business categories you declared. A valid code you are not enabled for is rejected just like one that does not exist — if the code you need is missing, that is an onboarding conversation, not an API problem.
</Warning>

## When it doesn't go straight through

| What happened | What to do |
| :--- | :--- |
| The payment has no checklist yet | Send `business_model` and `purpose_code`; the real requirement set appears on the next read |
| Something is still missing | Send just those fields or documents — what you already sent is kept |
| A field was refused on the finalizing call | Fix only the code the response names and send that again |
| The invoice number was already used | It is unique per merchant across filed verifications; raise a new one |
| The set was already filed | Staging is closed. Wait for it to be sent back, then correct it — see below for how you learn that |

## Four things that will bite you

**The buyer is the Indian remitter, not your customer abroad.** These fields describe whoever in India paid you, not the overseas party being paid. `buyer_postal_code` is stored as an Indian PIN code, so send the remitter's Indian address — filling this block with your own address is the most common way a first integration goes wrong.

**There is no amount to declare.** `invoice_amount` is not on the checklist — the amount that settles is the credit itself, read from the payment. There is no `principal`, no TCS, and no declaration field. All of them are a `400`, like any unknown key.

**Partial sends merge.** Three fields today and two tomorrow is five fields. Nothing you sent earlier is wiped, so send each thing as you get it rather than waiting for the full set.

**Editing closes the moment the set is filed.** While the payment is in review the fields and the invoice are frozen — no corrections, no swapping the file. If you spot a mistake after filing, wait for it to be sent back and fix it then.

## While it is in review

Ops either approves the verification, sends it back for changes, or rejects it. **None of the three raises a webhook** — poll [Get Verification Requirements](/api-reference/v3/b2b/verification-requirements) and read `settlement_status`:

| What you see | What happened | What you do |
| :--- | :--- | :--- |
| `UNDER_REVIEW` | Still with Ops, or approved — approval does not change this value | Nothing; wait for [`PAYMENT_SETTLED`](/api-reference/v3/webhooks/payment-settled) |
| back to `ACTION_REQUIRED` | Sent back for changes. Staging has reopened | Re-read the set, correct what is wrong, and file again |

A **rejection** does not move `settlement_status` either: the payment stays `UNDER_REVIEW` and a full refund is raised automatically. You will see it as a refund rather than as a verification state, so reconcile rejections against your refunds, not against this endpoint.

## After it settles: proof of delivery

Verification review is not the last compliance step. Once the money has reached you, one thing is still owed: evidence that the service was actually delivered. It does not gate your settlement — it is what backs the remittance if the transaction is ever examined.

1. Wait for [`PAYMENT_SETTLED`](/api-reference/v3/webhooks/payment-settled). Before that, the settlement-document endpoints refuse.
2. Upload each proof via [Upload Document](/api-reference/v3/b2b/upload-document) with `type=delivery_proof`, and keep each `ref`.
3. Attach them with [Attach Settlement Document](/api-reference/v3/b2b/attach-settlement-document), once per file. This flow takes **many** files under the single `delivery_proof` type.
4. Lock the set with [Submit Settlement Documents](/api-reference/v3/b2b/submit-settlement). At least one file is required, and after this nothing can be attached or deleted.

<Warning>
  **Submitting is final.** Read the set back with [List Settlement Documents](/api-reference/v3/b2b/list-settlement-documents) before you lock it — its `state` tells a draft from one already filed.
</Warning>

## What this flow never asks for

Integrations go wrong here more often by sending something extra than by leaving something out. The complete list of what has no place in a B2B services payment:

| | |
| :--- | :--- |
| Identity verification | None. No PAN, no IEC, no external register to clear. |
| HS code | Never. HS codes describe physical goods crossing a border. |
| Amount to declare | None. What settles is the credit itself, read from the payment. |
| Tax | None. Nothing is collected on top of the credit. |
| Declaration field | None. Filing a complete set is the declaration. |

Every one of them is a `400` if you send it, the same as any unknown key.
