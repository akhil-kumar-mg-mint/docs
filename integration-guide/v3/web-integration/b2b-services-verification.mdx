# Introduction

A rupee credit into a VBA creates a payment in **Action Required**. When the buyer is a business paying for a **service** — consultancy, software, professional fees, freight — the payment is made compliant through the same generic verification endpoint every classified payment uses, with the B2B services requirement set.

This guide walks that flow end to end: classify → read requirements → upload the invoice → submit → post-settlement documents.

<Note>
  **There is no PAN or identity step.** Unlike LRS (which verifies the remitter's PAN) and unlike B2B goods (which verifies the buyer's IEC), B2B services collects **no identity document at all**. The buyer name is a plain field you send — nothing is verified against an external register, and there is nothing to verify before you can proceed.
</Note>

<Note>
  **PSP callers must send `X-Merchant-ID`** on every call, naming the settling sub-merchant.
</Note>

## Step 1: Classify the payment

A payment with no `business_model` and `purpose_code` on its order has no requirement set yet. `GET` its verification and you get the classification stage back — the two facts to send, in the same shape checklist items use:

```bash
curl 'https://api-pacb-uat.eximpe.com/pg/payments/PR6938527534/verification/' \
  -H 'X-Client-ID: <client_id>' -H 'X-Client-Secret: <client_secret>' \
  -H 'X-Merchant-ID: <sub_merchant_id>' -H 'X-API-Version: 3.0.0'
```

```json
{
  "success": true,
  "message": "Verification requirements",
  "data": {
    "payment_id": "PR6938527534",
    "order_id": "OD3376378679",
    "settlement_status": "ACTION_REQUIRED",
    "business_model": null,
    "purpose_code": null,
    "fields": [
      { "code": "business_model", "message": "Business model (B2B or B2C)", "satisfied": false, "provided": false },
      { "code": "purpose_code", "message": "FEMA/FETERS purpose code for this order", "satisfied": false, "provided": false }
    ],
    "documents": []
  }
}
```

Send them through the same path's `POST`. They can ride along with everything else in one call, but nothing else can be validated until they land — so sending them first is the simplest thing to do:

```bash
curl -X POST 'https://api-pacb-uat.eximpe.com/pg/payments/PR6938527534/verification/' \
  -H 'X-Client-ID: <client_id>' -H 'X-Client-Secret: <client_secret>' \
  -H 'X-Merchant-ID: <sub_merchant_id>' -H 'X-API-Version: 3.0.0' \
  -H 'Content-Type: application/json' \
  -d '{ "fields": { "business_model": "B2B", "purpose_code": "S0802" }, "finalize": false }'
```

<Info>
  **Which purpose codes are B2B services?** `S0802`, `S0803`, `S1005`, `S1009`, `S1010`, `S1013`, `S1015`, `S1016`, `S1017`, `S1105`, `S1106` — all against `business_model: "B2B"`. They share one requirement set. The code must also be one your settling entity is enabled for.
</Info>

## Step 2: Read what the payment owes

With the payment classified, the same `GET` now returns the B2B services requirement set:

```json
{
  "success": true,
  "message": "Verification requirements",
  "data": {
    "payment_id": "PR6938527534",
    "order_id": "OD3376378679",
    "settlement_status": "ACTION_REQUIRED",
    "business_model": "B2B",
    "purpose_code": "S0802",
    "fields": [
      { "code": "buyer_name", "message": "Buyer / remitter name", "satisfied": true, "provided": true },
      { "code": "buyer_address_line_1", "message": "Buyer address line 1", "satisfied": false, "provided": false },
      { "code": "buyer_city", "message": "Buyer city", "satisfied": false, "provided": false },
      { "code": "buyer_state", "message": "Buyer state", "satisfied": false, "provided": false },
      { "code": "buyer_postal_code", "message": "Buyer PIN code", "satisfied": false, "provided": false },
      { "code": "buyer_email", "message": "Buyer email", "satisfied": false, "provided": false },
      { "code": "buyer_phone", "message": "Buyer phone", "satisfied": false, "provided": false },
      { "code": "invoice_number", "message": "Invoice number", "satisfied": false, "provided": false },
      { "code": "invoice_date", "message": "Invoice date", "satisfied": false, "provided": false }
    ],
    "documents": [
      { "code": "invoice", "message": "Commercial invoice", "satisfied": false, "provided": false }
    ]
  }
}
```

Nine fields and one document. What is still owed is the `satisfied: false` entries:

```js
const outstanding = [...data.fields, ...data.documents].filter(item => !item.satisfied)
```

`buyer_name` already reads `satisfied: true` here because the credit carried it — the requirement set accounts for what we already hold, so you only collect the rest.

<Note>
  **Do not hardcode the list.** Requirements are configuration. Reading them from this endpoint means a revision reaches your integration without a release on your side.
</Note>

<Warning>
  **`invoice_amount` is not asked for.** The amount that settles is the credit itself, and we take it from the payment — there is no figure to declare and no key to send. Sending one is a `400`, like any unknown key.
</Warning>

## Step 3: Upload the invoice

Upload the commercial invoice and keep the `ref`:

```bash
curl -X POST 'https://api-pacb-uat.eximpe.com/pg/payments/PR6938527534/documents/' \
  -H 'X-Client-ID: <client_id>' -H 'X-Client-Secret: <client_secret>' \
  -H 'X-Merchant-ID: <sub_merchant_id>' -H 'X-API-Version: 3.0.0' \
  -F 'type=invoice' \
  -F 'file=@invoice.pdf'
```

```json
{
  "success": true,
  "message": "Document uploaded",
  "data": { "ref": "a1b2c3d4-5e6f-7a8b-9c0d-1e2f3a4b5c6d", "type": "invoice" }
}
```

## Step 4: Submit the details

Send the remaining fields and the document `ref` under its checklist code. Partial sends merge, so you can spread this across calls — but the set only completes when nothing is outstanding.

```bash
curl -X POST 'https://api-pacb-uat.eximpe.com/pg/payments/PR6938527534/verification/' \
  -H 'X-Client-ID: <client_id>' -H 'X-Client-Secret: <client_secret>' \
  -H 'X-Merchant-ID: <sub_merchant_id>' -H 'X-API-Version: 3.0.0' \
  -H 'Content-Type: application/json' \
  -d '{
    "fields": {
      "buyer_name": "Northwind Technologies Pvt Ltd",
      "buyer_address_line_1": "7th Floor, Prestige Tower, Residency Road",
      "buyer_city": "Bengaluru",
      "buyer_state": "Karnataka",
      "buyer_postal_code": "560025",
      "buyer_email": "ap@northwind.co.in",
      "buyer_phone": "+919876543210",
      "invoice_number": "INV-2026-0041",
      "invoice_date": "2026-08-01"
    },
    "documents": [
      { "code": "invoice", "ref": "a1b2c3d4-5e6f-7a8b-9c0d-1e2f3a4b5c6d" }
    ],
    "finalize": true
  }'
```

The response says where the payment stands:

```json
{
  "success": true,
  "message": "Verification details received",
  "data": {
    "payment_id": "PR6938527534",
    "status": "in_review",
    "outstanding": []
  }
}
```

| `status` | Meaning |
| :--- | :--- |
| `incomplete` | Something is still owed — `outstanding` lists the codes. |
| `complete` | Everything was sent, but the set was staged rather than filed (`finalize: false`). |
| `in_review` | The complete set was filed. The payment is with EximPe Ops for review. |
| `action_required` | The complete set was filed and refused. Fix what is named and re-submit. |

<Note>
  There is no separate "submit" endpoint. `finalize` defaults to `true` and applies only to a **complete** set — it never forces an incomplete one through. Pass `finalize: false` to stage while you are still collecting.
</Note>

<Warning>
  **Staging closes once the verification is filed.** After the payment reaches `UNDER_REVIEW`, a further `POST` is refused rather than quietly editing the record that was filed. If Ops send the payment back, it reopens.
</Warning>

## Step 5: Post-settlement documents

Verification review is not the last compliance step. Once the payment **settles**, B2B services owes proof that the service was delivered.

<Steps>
  <Step title="Wait for settlement">
    [`PAYMENT_SETTLED`](/api-reference/v3/webhooks/payment-settled) fires. Before that, the settlement-document endpoints refuse.
  </Step>
  <Step title="Upload each proof">
    `POST /pg/payments/{payment_id}/documents/` with `type=delivery_proof`. Keep each `ref`.
  </Step>
  <Step title="Attach them">
    [Attach Settlement Document](/api-reference/v3/b2b/attach-settlement-document), once per file. B2B services takes **many** files under the single `delivery_proof` type.
  </Step>
  <Step title="Submit">
    [Submit Settlement Documents](/api-reference/v3/b2b/submit-settlement) locks the set. At least one `delivery_proof` is required, and after this nothing can be attached or deleted.
  </Step>
</Steps>

## How it differs from the other flows

| | B2B services | B2B goods | LRS (B2C education / travel) |
| :--- | :--- | :--- | :--- |
| Identity step | **none** | buyer IEC, verified against DGFT | remitter PAN, verified against income-tax records |
| Buyer name | plain field you send | locked to the verified IEC | locked to the verified PAN |
| HS code | never | always | never |
| Declaration field | not collected via the API | — | `buyer_declaration` |
| Documents at verification | commercial invoice | commercial invoice | varies by purpose code |
| Post-settlement documents | `delivery_proof`, many files | not available via the API | none |
| Completion via partner API | yes | not yet | yes |
