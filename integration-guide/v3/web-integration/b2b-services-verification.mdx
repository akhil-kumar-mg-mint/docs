A business in India has paid you for a service. We know the amount and the date; we do not know what the service was or who bought it. You tell us, we review it, and the payment settles.

<Note>
  **PSPs send `X-Merchant-ID` on every call here**, naming the sub-merchant the payment belongs to. The purpose codes you may declare come from that sub-merchant's account, not yours.
</Note>

## Do it in this order

There are two ways to collect: through [Create Order](/api-reference/v3/order/create) — Hosted Checkout or S2S UPI Intent — or by giving the buyer a **Virtual Account** to wire money into directly.

Create Order lets you declare `business_model: "B2B"` and a `purpose_code` on the order itself, whichever mode you use — that's the only pre-payment step this flow has, and doing it there means classification is already done by the time the payment lands. A Virtual Account credit has no Create Order call behind it, so classification always happens after the money arrives, through the steps below.

Either way, once the payment exists, the rest is the same:

<img src="/images/diagrams/b2b-services-verification-flow.svg" alt="Flowchart showing a B2B Services payment moving from webhook notification through document submission and review, ending in settlement abroad or a refund to the buyer." />

Submit is a loop, not a single call: send what you have, and later sends merge over earlier ones — nothing you sent already is wiped. Once the full set is in, the payment moves into review automatically.

## Classify it, then declare what the service was

A payment can arrive already classified — if you sent `business_model` and `purpose_code` on Create Order, [Get Verification Requirements](/api-reference/v3/b2b/verification-requirements) already shows both set, and you can skip ahead to the buyer and invoice fields below.

Otherwise there is nothing to check the payment against until you send both. They travel together, and only once: send one without the other and the call is refused naming the one you left out, and once set, sending either again is a `400`.

<Warning>
  **The first webhook you get is not reading this checklist.** Before classification, nothing claims the payment yet, so the event falls back to a legacy check and can name fields this flow never asks for. Ignore them, classify the payment, and read the real set from [Get Verification Requirements](/api-reference/v3/b2b/verification-requirements) instead.
</Warning>

Every services payment settles under one purpose code, paired with `business_model: "B2B"`, and you pick exactly one. There is no default and no way to leave it blank.

| Code | What it covers |
| :--- | :--- |
| `S0802` | Software consulting and implementation |
| `S0803` | Database and data processing |
| `S1005` | Accounting, auditing and bookkeeping |
| `S1009` | Architectural services |
| `S1010` | Agriculture and forestry services |
| `S1013` | Environmental services |
| `S1015` | Tax consulting |
| `S1016` | Market research and opinion polling |
| `S1017` | Publishing and printing |
| `S1105` | Museum, library and archival services |
| `S1106` | Recreation and sporting activities |

<Warning>
  **You can only send a code your merchant account is enabled for.** That list is set during KYC, from the business categories you declared. A valid code you're not enabled for is rejected just like one that doesn't exist — if the code you need is missing, that's an onboarding conversation, not an API problem.
</Warning>

## Send the details

Two calls. Upload the invoice first and keep the `ref` it returns, then send that ref alongside the fields — classifying facts included, if you have not sent them already.

**Uploading the invoice** is `multipart/form-data`:

```bash
curl -X POST 'https://api-pacb-uat.eximpe.com/pg/payments/<payment_id>/documents/' \
  -H 'X-Client-ID: <client_id>' -H 'X-Client-Secret: <client_secret>' \
  -H 'X-Merchant-ID: <sub_merchant_id>' \
  -H 'X-API-Version: 3.0.0' \
  -F 'type=invoice' \
  -F 'file=@invoice-SRV-0198.pdf'
```

That answers with a `ref` — a short numeric string, not a UUID:

```json
{ "data": { "ref": "8207383264", "type": "invoice" } }
```

**Sending the details** is one JSON call:

```json
{
  "fields": {
    "business_model": "B2B",
    "purpose_code": "S0802",
    "buyer_name": "Acme Technologies Pvt Ltd",
    "buyer_address_line_1": "4th Floor, Prestige Tower",
    "buyer_city": "Bengaluru",
    "buyer_state": "Karnataka",
    "buyer_postal_code": "560034",
    "buyer_email": "ap@acmetech.co.in",
    "buyer_phone": "+919876543210",
    "invoice_number": "EXP-2026-SRV-0198",
    "invoice_date": "2026-08-14"
  },
  "documents": [
    { "code": "invoice", "ref": "8207383264" }
  ]
}
```

That is the whole set — nine fields plus the classifying pair, and one document. `buyer_email` and `buyer_phone` are both required, not optional. Partial sends merge, so send what you have and fill in the rest later — a key outside this list is a `400`, not a silent drop.

The response says where the payment stands:

```json
{ "data": { "payment_id": "PR6938527534", "status": "incomplete", "outstanding": ["buyer_city", "invoice"] } }
```

`status` is `incomplete` while something is still owed, or `in_review` once the complete set has been filed and handed to our team for review. There is no `action_required` value here.

## Six things that will bite you

**There is no amount to send.** The amount that settles is the credit itself, read from the payment — you don't send it or confirm it separately.

**The buyer here is the Indian remitter, not your customer abroad.** These fields describe whoever in India paid you, not the overseas party being paid. `buyer_postal_code` is stored as an Indian PIN code, so send the remitter's Indian address.

**There is no HS code here.** Not part of this flow, and there is no field for one.

**Rejected is terminal, and the money goes straight back.** A rejection is not a stronger send-back. It closes the payment, and we automatically initiate a full refund to the buyer — you cannot resubmit or correct it. Only a **send-back** reopens the payment for editing. Read the decision, not just the fact that something came back.

**Proof of delivery comes after settlement, not before.** You can upload delivery-proof files any time, but filing the set is refused until the payment reaches `SETTLED`. Once it has, submit the full set in one call — holding your settlement waiting to file it is a mistake people make once.

**Editing closes the moment the set is filed.** While a payment is in review, the fields and the invoice are frozen — no corrections, no swapping the file. If you spot a mistake after filing, wait for the send-back and fix it then.

## After it settles: proof of delivery

Once the money has reached you, one thing is still owed: evidence that the service was actually delivered. It sits outside the verification flow — nobody reviews it, and it does not gate your settlement — but it is what backs the remittance if the transaction is ever examined.

Upload one or more files under `delivery_proof` via the same document endpoint as the invoice — a signed acceptance note, a milestone sign-off, a delivery confirmation email, a timesheet. You can upload these before the payment settles; only the next step is gated on `SETTLED`.

Once you have everything, file the set in a single call: send every `ref` you want on the record to [Submit Settlement Documents](/api-reference/v3/b2b/submit-settlement) as `refs`. That call names the whole set — a proof you uploaded and leave out of `refs` is dropped, not filed — and locks it in the same step. There's no separate attach call and no draft state; read the set back with [List Settlement Documents](/api-reference/v3/b2b/list-settlement-documents) first if you're unsure what you're holding.

<Warning>
  **Submitting is final.** A second submit is refused. Read `state` (`FRESH` or `SUBMITTED`) from [List Settlement Documents](/api-reference/v3/b2b/list-settlement-documents) before you call this.
</Warning>

## Payment statuses

Read `settlement_status` on the payment — [Get Verification Requirements](/api-reference/v3/b2b/verification-requirements) is where it lives. None of approval, send-back or rejection raises a webhook on this flow, so polling this field is how you find out which happened.

| `settlement_status` | What it means | What you do |
| :--- | :--- | :--- |
| `ACTION_REQUIRED` · `INFO_PENDING` | We have the money but not an accepted set of details — either you have not submitted yet, or we sent it back | Read the comment, fix what it names, submit again |
| `UNDER_REVIEW` | Filed and with our team. Editing is closed. Also what a rejection leaves the payment showing — see below. | Wait |
| `VERIFIED` · `READY_FOR_SETTLEMENT` · `SETTLED` | Approved. Settlement follows. No webhook fires for the approval itself. | Upload proof of delivery once it settles |
| `EXPIRED` · `ON_HOLD` | The window closed, or the payment is held, before a set was accepted. Terminal — the money returns to the buyer. | Nothing to recover |

A rejection does not move `settlement_status` to anything named "rejected" — the payment stays `UNDER_REVIEW`, and we automatically raise a full refund. You learn about it from the refund rather than from this field.

<Warning>
  **A send-back never discards what you sent.** The buyer details, the invoice fields and the uploaded file are all still there. Change only what the comment asks about and submit the set again.
</Warning>
